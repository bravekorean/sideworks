# SideWorks

SideWorks는 전자결재와 조직 관리를 중심으로 개발하는 그룹웨어 MVP입니다.
Spring Boot와 React를 기반으로 설계·구현하며, 개발 과정에서의 기술 선택과 문제 해결을 학습하고 취업 포트폴리오로 정리하는 것을 목표로 합니다.

V1의 핵심 기능, 프론트엔드 API 연동, JWT 자동 재발급, Swagger/OpenAPI 문서화와 AWS 배포 검증을 완료했습니다. 현재는 V1을 기준선으로 보존하고 V2 고도화를 준비하고 있습니다.

## 주요 기능

- JWT 기반 로그인과 권한 관리
- 사용자·부서·직급 관리
- 전자결재 작성, 상신, 승인, 반려, 취소
- 결재선·참조자·처리 이력 관리
- 마이페이지
- React/MUI 기반 관리 화면과 대시보드
- Swagger/OpenAPI 기반 API 명세

## V1 진행 상태

- 완료: 인증·인가, 사용자·부서·직급 관리, 마이페이지, 전자결재, 통합 검색, 대시보드
- 완료: React 화면과 백엔드 API 연동, Access Token 자동 재발급 검증
- 완료: 역할별 접근 검증 및 Swagger/OpenAPI 문서화
- 완료: AWS EC2·RDS·Nginx 기반 배포와 로그인부터 결재 완료까지의 운영 환경 스모크 테스트
- 완료: 작성자·결재자·참조자 관점의 문서 상태와 실제 RDS 데이터 반영 확인

배포는 일회성 검증 환경에서 수행했으며, 검증과 화면 기록 후 과금 방지를 위해 클라우드 자원을 정리했습니다. 재현 가능한 구성과 트러블슈팅 과정은 별도 배포 문서에 값이 아닌 절차 중심으로 기록했습니다.

## 기술 스택

- Backend: Java 21, Spring Boot 3.5, Spring Security, Spring Data JPA, QueryDSL, springdoc-openapi
- Database: MySQL 8.0
- Frontend: React 19, MUI
- Authentication: JWT Access Token, Refresh Token Cookie

## V2 고도화 계획

V2는 V1의 핵심 업무 흐름을 유지하면서 결재 자동화, 조직 가시성, 실시간 기능과 운영 품질을 Vertical Slice 단위로 확장하는 것을 목표로 합니다. 기능 하나를 백엔드·프론트엔드·테스트·문서까지 완료한 뒤 다음 기능으로 이동합니다.

### 1단계: V1 안정화

- 인증 실패 응답의 `401 Unauthorized`와 `403 Forbidden` 구분
- 핵심 상태 전이와 잘못된 입력에 대한 테스트 보완
- 실제 실행 SQL, N+1, QueryDSL 페이징과 인덱스 점검
- 사용자 증가에 대비한 검색·필터의 서버 쿼리 및 페이지네이션 전환

새 기능 전에 V1의 기준 동작과 성능 측정 방법을 먼저 고정하면 이후 회귀 오류와 성급한 최적화를 줄일 수 있습니다.

### 2단계: 조직도와 결재 기능 고도화

- 계층형 부서 데이터를 이용한 조직도
- 결재 종류별 결재선 템플릿
- 부서와 직급을 기반으로 한 자동 결재선
- 위임, 전결, 합의 등 복합 결재 정책
- 사용자별 세부 권한 부여

결재선 템플릿은 실제 결재선을 생성하는 용도로만 사용하고, 상신 이후의 결재 처리는 V1과 동일하게 문서별 결재선 데이터를 기준으로 수행합니다.

### 3단계: 실시간 알림과 협업

- SSE 기반 결재 요청·승인·반려 알림
- 결재함 건수 실시간 갱신
- WebSocket 기반 결재건별 협업 채팅
- 결재 완료 후 채팅방 종료와 대화 내역 보존

모든 결재 문서에 채팅방을 자동 생성하지 않고, 작성자나 현재 결재자가 논의가 필요할 때 생성하는 방식을 사용합니다. 참조자는 논의를 요청하고 현재 결재자가 승인하면 참여할 수 있도록 설계할 예정입니다.

### 4단계: 통계와 운영 품질

통계는 개인의 성과 순위를 매기는 것이 아니라 조직의 결재 흐름과 업무 병목을 파악하는 것을 목적으로 합니다.

| 역할 | 조회 범위 |
| --- | --- |
| `USER` | 본인이 소속된 부서의 집계 통계 |
| `ADMIN` | 담당 부서의 상세 통계와 장기 미처리 현황 |
| `SUPER_ADMIN` | 조직 전체, 부서 비교, 사용자별 결재 처리 현황 |

- 주·월 단위 결재 생성, 진행, 완료 건수와 평균 처리 시간
- 작성자와 결재자 관점을 분리한 사용자별 처리 현황
- 관리자 작업과 민감한 통계 조회에 대한 감사 로그
- 실제 조회 조건과 실행 계획을 근거로 한 DB 인덱스 최적화

일반 사용자에게 개인 성과 통계를 제공하지 않으며, 사용자별 통계는 `SUPER_ADMIN`만 조회할 수 있도록 서버에서 권한을 검증합니다.

### 확장 원칙

Redis와 Kafka는 사용 경험을 보여주기 위해 미리 도입하지 않습니다. 단일 서버 환경에서는 SSE와 WebSocket으로 시작하고, 실제 병목이나 다중 서버 메시지 전달, 캐시 또는 이벤트 내구성 요구가 확인될 때 도입 여부를 다시 검토합니다. 통계 역시 개인 순위가 아니라 결재 병목과 조직 운영 개선을 위한 지표로 제한합니다.

SideWorks 프로젝트 정리

학습 및 취업 포트폴리오 목적의 그룹웨어 MVP 프로젝트 정리 문서

1. 프로젝트 개요

SideWorks는 학습 및 취업 포트폴리오를 목적으로 개발하는 그룹웨어 MVP 프로젝트이다.

단순히 기능을 구현하는 것보다, 실제 백엔드 개발에서 자주 마주치는 사용자 관리, 권한, 인증, 조직 구조, 전자결재 흐름을 직접 설계하고 구현해보는 것을 목표로 한다.

주요 기능

  • JWT 기반 로그인
  • 사용자 관리
  • 부서 및 직급 관리
  • 권한 기반 API 접근 제어
  • 전자결재
  • 결재선 관리
  • 결재 이력 관리
  • 참조자 관리
  • 관리자 화면 연동
  • React 기반 프론트엔드 연동

이 프로젝트는 개인 학습 프로젝트이지만, 가능한 한 실제 업무 시스템에서 발생할 수 있는 흐름을 고려하며 설계하고 있다.

예를 들어 사용자는 반드시 부서와 직급을 가진다는 단순한 가정보다, 실제 입사·배정 흐름을 고려하여 미배정 상태를 허용하는 구조로 변경하였다.

2. 프로젝트 주제 선정 이유

그룹웨어는 사용자, 조직, 권한, 결재, 이력 관리 등 백엔드 개발자가 반드시 이해해야 하는 요소를 한 번에 다룰 수 있는 주제라고 판단했다.

단순 게시판보다 도메인이 복잡하고, 실무 시스템과 가까운 구조를 경험할 수 있다는 점에서 학습 가치가 높다.

  • 사용자와 권한 관리
  • 부서와 직급 같은 조직 구조 설계
  • 전자결재의 상태 변화와 이력 관리
  • JWT 로그인과 Spring Security 설정
  • DB 제약조건과 실제 업무 흐름의 관계
  • JPA Entity 연관관계 설계
  • 프론트엔드와 백엔드 API 연동

포트폴리오 관점에서도 “왜 이렇게 설계했는지”를 설명할 수 있는 요소가 많다고 판단했다.

3. 개발 방식과 역할 분담

이 프로젝트는 사용자와 Codex Agent가 페어 프로그래밍 방식으로 진행한다.

나의 역할

  • 요구사항 고민
  • DB 설계 방향 결정
  • 코드 직접 작성
  • 예제 코드 이해 및 적용
  • 오류 상황 공유
  • Postman을 통한 API 테스트
  • 설계 변경 판단
  • 학습 내용 정리

중요한 점은 단순히 코드를 복사하는 것이 아니라, 왜 해당 구조를 사용하는지 질문하고 이해하려는 방식으로 진행한다는 것이다.

Codex Agent의 역할

  • 설계 방향 제안
  • 예제 코드 제공
  • 사용자가 작성한 코드 리뷰
  • 오류 원인 분석
  • DB 설계 피드백
  • 보안상 위험 요소 안내
  • 테스트 코드 작성 보조
  • 단계별 개발 순서 제안
설계 설명
→ 예제 코드 제시
→ 사용자가 직접 구현
→ 코드 리뷰
→ 필요한 경우 개선

4. 기술 스택 선정 이유

Java 21

Java 21은 최신 LTS 버전이며 Spring Boot 3.x와 함께 사용하기 적합하다.

  • 장기 지원 버전
  • 최신 Java 문법과 기능 학습 가능
  • Spring Boot 3.5.x와 호환
  • Virtual Thread 같은 최신 동시성 기능을 향후 실험 가능

현재 V1에서는 Virtual Thread를 적용하지 않는다. MVP 단계에서는 인증, JPA, DB 설계, 전자결재 도메인 구현이 더 중요하다고 판단했다.

Spring Boot 3.5.x

Spring Boot는 REST API 서버를 빠르게 구성할 수 있고, 실무 백엔드 개발에서 널리 사용되는 프레임워크이다.

  • REST API 서버 구현에 적합
  • Spring Security, JPA, Validation과 통합이 좋음
  • 설정 자동화가 잘 되어 있음
  • 실무 백엔드 개발에서 많이 사용됨

Spring Security

로그인, 인증, 권한 처리를 구현하기 위해 사용한다.

  • 인증과 인가의 차이
  • SecurityConfig
  • permitAll, authenticated
  • SecurityContext
  • JWT 인증 필터
  • PasswordEncoder와 BCrypt 비밀번호 검증

JWT

프론트엔드와 백엔드가 분리된 구조에서 stateless 인증을 구현하기 위해 JWT를 사용했다.

  • 로그인 성공 시 accessToken 발급
  • accessToken은 응답 body로 반환
  • refreshToken은 HttpOnly Cookie로 반환
  • 인증이 필요한 API는 Authorization: Bearer {accessToken} 헤더로 호출

Spring Data JPA

DB 테이블과 Java Entity를 매핑하고 Repository 패턴을 학습하기 위해 사용했다.

  • Entity와 Table 매핑
  • @ManyToOne
  • Lazy Loading
  • Repository 메서드 네이밍 규칙
  • 트랜잭션 범위
  • Entity를 직접 응답하지 않고 DTO로 변환하는 이유

QueryDSL

복잡한 조회 조건과 동적 쿼리를 안정적으로 작성하기 위해 도입했다.

  • 문자열 기반 JPQL보다 안정적
  • 컴파일 시점에 오류 확인 가능
  • 복잡한 검색 조건 확장에 유리
  • 실무에서 자주 사용됨

기존 QueryDSL 의존성에서 취약점 경고가 발생하여, OpenFeign QueryDSL 버전으로 교체하였다.

MySQL 8.0

관계형 데이터베이스 설계와 제약조건을 학습하기 위해 사용했다.

  • PK / FK
  • UNIQUE 제약조건
  • NOT NULL 제약조건
  • nullable 설계
  • FK와 업무 흐름의 관계
  • CASCADE / RESTRICT
  • 인덱스 네이밍

React 19

백엔드 API와 분리된 프론트엔드 화면을 구성하기 위해 React를 사용한다.

  • SPA 구조 학습
  • REST API 연동 학습
  • 로그인 후 accessToken을 이용한 API 호출 구조 학습
  • 포트폴리오 화면 구현에 적합

MUI

직접 CSS를 모두 작성하기보다 빠르게 관리자 화면을 구성하기 위해 MUI를 사용한다.

  • 기본 UI 컴포넌트 제공
  • 관리자 페이지 구성에 적합
  • 이미 프로젝트에 설치되어 있어 추가 전환 비용이 적음
  • CSS 작성 시간을 줄이고 기능 구현에 집중 가능

5. 전체 아키텍처 구조

현재 백엔드 구조는 전형적인 계층형 구조를 따른다.

Controller
→ Service
→ Repository
→ Entity
→ DB

요청과 응답에는 DTO를 사용한다.

HTTP 요청 JSON
→ Controller
→ Request DTO
→ Service
→ Entity 변경 또는 조회
→ Repository
→ DB

Controller

Controller는 HTTP 요청과 응답을 담당한다. 요청 URL 매핑, Request DTO 수신, Service 호출, ResponseEntity 반환을 담당하며 비즈니스 로직은 직접 처리하지 않는다.

Service

Service는 비즈니스 로직을 담당한다. 사용자 생성, 중복 검증, 권한 변경, 상태 변경, 부서/직급 배정 같은 업무 규칙을 처리한다.

Repository

Repository는 DB 접근을 담당한다.

Optional<User> findByLoginId(String loginId);

List<User> findAllByDepartmentIsNullOrPositionIsNull();

DTO

DTO는 API 요청과 응답에 사용하는 객체이다.

  • Entity 내부 구조 노출 방지
  • Lazy Loading 문제 완화
  • API 응답 형식 안정화
  • 화면에 필요한 필드만 반환 가능
  • Entity 변경이 API 스펙 변경으로 바로 이어지는 것을 방지

Entity

Entity는 DB 테이블과 매핑되는 객체이다.

  • User
  • Department
  • Position
  • Approval
  • ApprovalLine
  • ApprovalHistory
  • ApprovalCarbonCopy

Enum

Enum은 정해진 값만 허용하기 위해 사용한다.

public enum UserRole {
    SUPER_ADMIN,
    ADMIN,
    USER
}

6. DB 설계 흐름

초기 DB 설계

초기에는 department_id, position_id를 NOT NULL로 설정했다.

그룹웨어 시스템에서 사용자는 보통 부서와 직급을 가진다고 생각했기 때문이다.

설계 변경 계기

개발 중 실제 업무 흐름을 고려하면서 다음 문제가 생겼다.

1. 사용자가 먼저 회원가입한다.
2. 회원가입 직후에는 부서와 직급이 없을 수 있다.
3. 관리자가 미배정 사용자 목록을 조회한다.
4. 이후 부서와 직급을 배정한다.

또한 경력직 입사자의 경우 직급은 정해져 있지만 부서 배정이 아직 미정일 수 있다고 판단했다.

department 있음 / position 있음
→ 정상 배정 완료

department 없음 / position 있음
→ 부서 미배정

department 있음 / position 없음
→ 직급 미배정

department 없음 / position 없음
→ 완전 미배정

변경된 DB 설계

ALTER TABLE sidework.usertbl
    MODIFY department_id BIGINT NULL,
    MODIFY position_id BIGINT NULL;

JPA Entity에서도 nullable = false를 제거했다.

@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "department_id")
private Department department;

@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "position_id")
private Position position;

핵심: NULL은 허용하지만, 값이 들어가는 경우에는 반드시 실제 존재하는 부서 또는 직급 ID여야 한다. 즉 FK는 유지한다.

7. 인증 / JWT 흐름

로그인 흐름

POST /api/auth/login
{
  "loginId": "admin",
  "password": "1234"
}
AuthController
→ AuthService
→ UserRepository.findByLoginId()
→ PasswordEncoder.matches()
→ JwtTokenProvider.createAccessToken()
→ JwtTokenProvider.createRefreshToken()
→ accessToken 응답 body 반환
→ refreshToken HttpOnly Cookie 반환

Access Token

accessToken은 API 요청 인증에 사용한다.

Authorization: Bearer {accessToken}

Refresh Token

refreshToken은 HttpOnly Cookie로 반환한다.

Set-Cookie: refreshToken=...; HttpOnly; SameSite=Lax

HttpOnly를 사용하는 이유는 JavaScript에서 refreshToken에 직접 접근하지 못하도록 하기 위해서이다.

JwtAuthenticationFilter

1. Authorization 헤더 확인
2. "Bearer " 접두어 확인
3. 실제 token 추출
4. token 유효성 검증
5. token에서 userId, loginId, role 추출
6. UsernamePasswordAuthenticationToken 생성
7. SecurityContext에 Authentication 등록
8. 다음 필터 또는 Controller로 요청 전달

11. 트러블슈팅 기록

로그인 API 호출 시 403 발생

문제: Postman에서 로그인 API 호출 시 403 Forbidden이 발생했다.

원인: 로그인 API는 POST 요청을 받지만, GET 요청으로 호출한 경우가 있었다.

해결: Postman에서 메서드를 POST로 변경하고 Body에 JSON을 넣어 요청했다.

비밀번호가 계속 틀리다고 나오는 문제

문제: DB에 admin 계정이 있었지만 로그인 실패 응답이 발생했다.

원인: DB의 user_pass 값이 입력한 비밀번호와 매칭되는 BCrypt 해시가 아니었다.

해결: 입력 비밀번호에 해당하는 BCrypt 해시를 DB에 저장하여 해결했다.

Authorization 헤더 문제

문제: 인증이 필요한 API 호출 시 403 Forbidden이 발생했다.

원인: Authorization 헤더에 accessToken만 넣고 Bearer 접두어를 붙이지 않은 경우가 있었다.

해결: Authorization: Bearer {accessToken} 형식으로 헤더를 추가했다.

Gradle DataSource 설정 문제

문제: Spring Boot 실행 시 DataSource 설정 오류가 발생했다.

원인: DB 접속 정보가 설정 파일 또는 활성화된 profile에 제대로 설정되지 않았다.

해결: 로컬 환경용 설정 파일에 datasource 정보를 분리하고, 민감정보가 Git에 올라가지 않도록 .gitignore에 포함했다.

QueryDSL 취약점 경고

문제: 의존성 검사에서 QueryDSL 관련 취약점 경고가 발생했다.

원인: 기존 QueryDSL 의존성 버전에 알려진 취약점이 있었다.

해결: OpenFeign QueryDSL 버전으로 교체하여 경고를 제거했다.

13. V2 확장 설계 방향

V2에서는 Redis와 Kafka 도입을 처음 고려했지만, 현재 프로젝트 규모에서는 오버엔지니어링일 수 있다고 판단했다.

대신 실시간 알림과 채팅 기능을 SSE와 WebSocket으로 설계하기로 했다.

SSE
→ 결재 요청 알림
→ 결재 승인/반려 알림
→ 새 결재건 알림
→ 처리해야 할 결재건 알림

WebSocket
→ 결재건별 채팅방
→ 부서별 채팅방
→ 관리자 채팅방

SSE를 선택한 이유

SSE는 서버에서 클라이언트로 이벤트를 전달하는 단방향 통신에 적합하다.

결재 알림은 서버가 사용자에게 알림을 보내는 구조이므로 SSE가 적합하다고 판단했다.

WebSocket을 선택한 이유

WebSocket은 양방향 실시간 통신에 적합하다.

채팅은 클라이언트와 서버가 서로 메시지를 주고받아야 하므로 WebSocket이 적합하다.

결재건별 채팅방 설계 방향

모든 결재건에 채팅방을 자동 생성하지 않는다. 단순 비품 요청이나 정형 결재처럼 논의가 필요 없는 결재건도 있기 때문이다.

따라서 채팅방은 필요할 때 생성하는 Lazy Creation 방식으로 설계한다.

작성자
- 논의하기 클릭 시 즉시 채팅방 생성 가능

현재 결재자
- 논의하기 클릭 시 즉시 채팅방 생성 가능

참조자
- 직접 채팅방 생성 불가
- 논의 요청 가능
- 현재 결재자가 승인하면 채팅방 생성
- 거절하면 생성되지 않음

채팅방이 생성되면 참여자는 작성자, 결재선 전체 결재자, 참조자가 된다.

결재 완료 / 반려 / 취소
→ 채팅방 CLOSED
→ 이후 메시지 작성 불가
→ 기존 대화 조회 가능
→ export 가능

채팅 메시지와 애플리케이션 로그의 구분

채팅 메시지는 업무 데이터이므로 DB에 저장한다.

반면 애플리케이션 로그는 장애 추적과 운영 관리를 위한 데이터이다.

log.info("CHAT_MESSAGE_SENT chatRoomId={}, senderId={}, messageId={}",
        chatRoomId, senderId, messageId);

로그에는 메시지 원문을 남기지 않고, 식별자 중심으로 남긴다.

채팅방 열람 및 보존 정책

결재건별 채팅은 업무 의사소통 이력에 해당하므로, 결재가 완료되어 채팅방이 닫히더라도 대화 내역은 보존해야 한다.

채팅방 종료 = 더 이상 메시지를 주고받지 못하는 상태
채팅방 삭제 = 데이터 자체를 지우는 것

일반 사용자는 본인이 참여한 채팅방만 조회 가능하고, 관리자는 감사 목적 열람 시 사유 입력과 열람 이력 저장이 필요하다.

14. 현재 느낀 점

개발을 하면 할수록 단순히 코드를 작성하는 것보다 “왜 이렇게 설계하는지”를 고민하는 것이 중요하다는 것을 느꼈다.

특히 DB 설계는 처음부터 완벽하게 정해지는 것이 아니라, 실제 업무 흐름을 생각하면서 변경될 수 있다는 점을 배웠다.

초기에는 사용자가 반드시 부서와 직급을 가져야 한다고 생각했지만, 회원가입과 인사 배정 흐름을 고려하면서 nullable 구조가 더 자연스럽다는 결론을 내렸다.

예전에 솔루션 개발과 엔지니어 업무를 하면서 당시에는 최선이라고 생각했던 해결 방식이, 시간이 지나 공부를 다시 해보니 반드시 최선은 아니었을 수 있다는 것도 느끼게 되었다.

같은 문제라도 요구사항, 운영 환경, 유지보수 관점에 따라 더 나은 설계가 존재할 수 있다는 점을 이해하게 되었다.

또한 Codex Agent를 사용하면서 AI 도구가 단순히 코드를 대신 작성해주는 도구가 아니라, 설계 방향을 함께 검토하고 코드 리뷰를 도와주며 학습 흐름을 잡아주는 페어 프로그래밍 파트너가 될 수 있다는 것을 체감했다.

기존에 사용하던 ChatGPT와 달리 Codex Agent는 실제 프로젝트 파일을 함께 확인하고, 내가 작성한 코드를 기반으로 피드백을 주며, 단계적으로 구현을 이어갈 수 있다는 점에서 개발 경험이 많이 달랐다.

AI는 생각보다 훨씬 가까이 와 있었고, 중요한 것은 AI가 작성한 코드를 그대로 사용하는 것이 아니라 그 구조를 이해하고 내 것으로 만드는 과정이라고 느꼈다.

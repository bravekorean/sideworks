# SideWorks의 AI 협업 방식

마지막 갱신: 2026-09-07

SideWorks는 개발자가 Codex Agent를 학습 도구이자 페어 프로그래밍 파트너로 활용해 진행한 프로젝트다. AI 사용 사실을 숨기기보다 역할과 검증 과정을 명확하게 기록한다.

## 1. 역할 구분

### 개발자

- 프로젝트 주제와 요구사항 결정
- 실제 업무 경험을 바탕으로 도메인 정책 제안
- DB 구조와 기능 우선순위 결정
- 예제 코드를 이해하고 직접 구현
- Postman과 브라우저를 이용한 통합 검증
- 오류 재현과 로그·DB 상태 확인
- AI 제안의 채택, 수정 또는 보류 결정

### Codex Agent

- 구현 순서와 설계 대안 제시
- Spring, JPA, JWT와 React 개념 설명
- 예제 코드 및 반복 작업 지원
- 코드 구조, 보안과 유지보수 관점 리뷰
- 오류 원인 후보 분석과 검증 방법 제안
- 테스트, 리팩토링과 문서화 지원

최종 요구사항과 설계 선택의 책임은 개발자에게 있으며, Codex의 결과는 검증 없이 그대로 정답으로 취급하지 않는다.

## 2. 기본 협업 흐름

```text
문제와 요구사항 정의
→ Codex가 대안과 장단점 설명
→ 개발자가 방향 결정
→ 개발자가 직접 구현하거나 명시적으로 구현 요청
→ 컴파일·테스트·브라우저·DB로 검증
→ 문제와 결정 과정을 문서화
```

학습 효과가 중요한 기능은 설명과 예제를 바탕으로 개발자가 먼저 작성했다. 반복 수정, 명세 어노테이션 적용이나 책임이 명확한 리팩토링은 개발자가 범위를 승인한 뒤 Codex가 수행하기도 했다.

## 3. AI 제안을 수정한 사례

### 실제 의존성 버전 확인

SpringDoc 보안 경고를 해결하는 과정에서 상위 라이브러리 버전만으로 안전 여부를 판단하지 않고 `dependencyInsight`를 실행했다. 그 결과 BOM이 취약한 전이 의존성을 최종 선택하고 있음을 확인하여 관리 버전을 직접 재정의했다.

이 사례는 AI의 초기 설명도 실제 빌드 결과와 다를 수 있으며, 공식 자료와 실행 결과로 다시 검증해야 한다는 점을 보여준다.

### 업무 경험을 반영한 nullable 설계

초기에는 사용자가 반드시 부서와 직급을 가져야 한다고 가정했지만, 개발자가 실제 입사·이동 과정의 미배정 기간을 제시했다. 이를 바탕으로 FK는 유지하면서 부서와 직급을 nullable로 변경했다.

### 과도한 기술 도입 보류

Redis, Kafka와 Spring Batch를 학습 목적으로 추가하는 방안을 논의했으나 현재 규모와 요구사항에는 과도하다고 판단했다. 실시간 알림은 SSE, 협업 채팅은 WebSocket으로 시작하고 구체적인 병목이 확인될 때 확장하기로 결정했다.

## 4. 품질과 보안 규칙

- 파일과 의존성 변경은 범위를 설명하고 개발자 승인 후 수행한다.
- 비밀번호, JWT Secret, DB 계정과 환경변수 값은 대화·문서·저장소에 복사하지 않는다.
- 기존 변경사항을 임의로 되돌리지 않는다.
- 핵심 비즈니스 규칙은 자동화 테스트 또는 통합 시나리오로 확인한다.
- 확인하지 않은 내용을 완료된 기능처럼 문서화하지 않는다.
- 디자인 패턴과 계층은 실제 책임 분리가 필요할 때만 도입한다.

## 5. AI 활용에서 얻은 학습

AI는 구현 속도를 높이고 넓은 대안을 빠르게 확인하는 데 유용했지만, 프로젝트의 품질은 질문의 구체성, 도메인 이해와 검증 능력에 좌우됐다. 특히 컴파일 성공, 테스트 통과, 실제 SQL과 브라우저 Network 결과처럼 재현 가능한 근거가 설계 설명보다 우선한다는 점을 학습했다.

V2에서는 큰 계층을 한 번에 구현하는 대신 하나의 기능을 백엔드, 프론트엔드, 테스트와 문서까지 끝내는 Vertical Slice 방식으로 협업을 개선할 예정이다.

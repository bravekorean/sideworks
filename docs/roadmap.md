# SideWorks 개발 현황과 로드맵

마지막 갱신: 2026-09-07

> 이 문서는 실제 코드와 검증 결과를 기준으로 `V1 완료`, `알려진 한계`, `V2 개선 백로그`를 구분한다. API 또는 화면 파일이 존재하더라도 실제 통합 검증이 끝나지 않았다면 완료로 과장하지 않는다.

## 1. 현재 위치

V1의 백엔드 핵심 기능과 React 화면의 실제 API 연동을 완료했다. 로그인부터 Access Token 자동 재발급, 사용자·부서·직급 관리, 전자결재와 통합 검색의 주요 브라우저 시나리오도 확인했다.

Swagger/OpenAPI 문서화를 적용하고 전체 자동화 테스트를 통과했다. AWS EC2·RDS·Nginx 환경에 배포하여 로그인, 결재 상신, 결재 대기 조회, 승인 완료, 처리함과 참조함 반영까지 스모크 테스트했다. 배포 구조와 문제 해결 과정을 공개 가능한 형태로 문서화했으며, 일회성 검증에 사용한 클라우드 자원은 과금 방지를 위해 정리했다.

따라서 V1은 완료 상태이며 현재 남은 개발 범위는 V2 고도화와 V1에서 의도적으로 미룬 품질 개선이다.

## 3. V1의 알려진 한계와 개선 후보

### 프론트엔드 인증 보완

백엔드 재발급 API와 프론트엔드 Axios 응답 인터셉터를 연결했다. 여러 요청이 동시에 실패해도 하나의 재발급 요청을 공유하며, 성공 시 원래 요청을 새 토큰으로 재시도한다.

백엔드 기본 인증 실패가 `403`으로 반환될 수 있어 프론트는 `401` 또는 만료된 JWT와 함께 발생한 `403`을 재발급 대상으로 처리한다. 짧은 Access Token 유효시간을 적용해 `/api/auth/refresh`의 `200 OK`와 원래 요청 재시도를 브라우저에서 확인했다. 전용 Protected Route 또는 공통 인증 상태 관리 구조는 V1에 도입하지 않았다.

### 관리자 화면

사용자, 부서와 직급 화면을 실제 API에 연결하고 주요 생성·조회·수정·상태 변경 시나리오를 브라우저와 배포 환경에서 확인했다.

부서 화면의 소속 인원 수는 별도 통계 API가 아니라 관리자 사용자 목록을 함께 조회하여 프론트에서 계산한다. 데이터가 커지면 전용 집계 API가 필요하다.

사용자 관리 화면은 V1 규모를 고려해 최대 100명을 조회한 뒤 프론트에서 검색·필터링한다. 사용자 수가 증가하면 검색 조건과 필터를 서버 쿼리 및 페이지네이션으로 옮겨야 한다.

### 대시보드

프로필, 결재함 건수, 결재 대기 문서와 최근 활동은 실제 API를 사용한다. 최근 활동은 본인이 작성자·결재자·참조자로 참여한 문서의 `ApprovalHistory`만 최신순으로 조회하며, 다른 사용자의 무관한 결재 이력은 노출하지 않는다. 각 데이터를 병렬 조회하는 현재 방식은 V1에서는 단순하지만, 규모가 커지면 대시보드 전용 집계 API로 합쳐 요청 수와 DB 조회를 줄이는 것이 적절하다.

### 전자결재

기능과 화면 연결을 완료하고 여러 사용자 계정으로 상신, 순차 승인, 반려, 권한 범위와 상세 조회를 확인했다. 배포 환경에서는 상신부터 최종 승인, 처리함과 참조함 반영까지 대표 시나리오를 스모크 테스트했다.

상신 취소 후 결재선의 `PENDING` 상태가 남아 취소 문서가 결재 대기함에 표시되던 오류를 수정했다. 결재 대기 조회는 결재선 상태뿐 아니라 문서 상태가 `IN_PROGRESS`인지 함께 검사한다. 참조함에서는 취소 사실도 업무 이력이므로 `CANCELED` 상태의 문서를 유지한다.

### 통합 검색

상단 검색창은 `GET /api/approvals/search`와 연결되었다. 제목 또는 작성자·결재자·참조자의 이름, 로그인 ID, 사번에 검색어가 포함된 문서를 찾는다. 일반 사용자는 자신이 참여한 문서만 검색하며 `SUPER_ADMIN`은 전체 문서를 검색할 수 있다. 사용자 상세 Drawer보다 수정 Dialog가 뒤에 표시되던 레이어 충돌도 수정하여 상태·역할·부서·직급 변경 화면을 조작할 수 있게 했다.

## 4. V2로 이관한 개선 백로그

### 선택적 개선 기능

* 인증이 필요한 라우트를 명시적으로 보호하는 공통 구조 검토
* 데이터 증가 시 사용자 관리 검색·필터를 서버 쿼리로 이전

대시보드 업무 현황은 V2의 조직 통계나 개인 성과 통계와 구분한다.

### 품질과 운영

* 전체 Postman 시나리오 문서 최종 정리
* 잘못된 입력과 상태 전이에 대한 테스트 보완
* 실제 실행 SQL, N+1과 QueryDSL 페이징 점검
* V1 전체 리팩토링과 보안 점검
* 인증 실패 응답의 `401 Unauthorized`와 `403 Forbidden` 구분
* Refresh Token 저장·회전·강제 폐기 정책 검토

## 5. V2 권장 작업 순서

1. V1 회귀 테스트와 인증 오류 응답 정리
2. 계층형 부서 기반 조직도 구현
3. 결재선 템플릿과 부서·직급 기반 자동 결재선 구현
4. SSE 기반 결재 알림과 결재함 카운트 갱신
5. 역할별 조직·결재 통계와 감사 로그 구현
6. 실제 사용 시나리오에서 필요성이 확인되면 WebSocket 협업 채팅 구현
7. 각 단계별 실행 SQL·보안·성능 검증과 문서 갱신

조직도부터 시작하는 이유는 현재의 계층형 부서 모델을 재사용하면서 V2의 화면·조회 구조를 비교적 낮은 위험으로 확장할 수 있기 때문이다. 자동 결재선은 실제 결재 데이터 생성 규칙에 영향을 주므로 조직도 다음에 테스트 주도로 진행한다. 실시간 기능과 통계는 안정된 도메인 이벤트와 조회 기준이 마련된 뒤 추가한다.

## 7. V2 계획

### 결재 고도화

* 결재선 템플릿
* 부서·직급 기반 자동 결재선
* 위임, 전결, 합의 등 복합 결재 정책
* 사용자별 세부 권한

결재선 템플릿은 문서 상신 시 실제 `approval_linetbl` 데이터를 생성하는 원본으로만 사용한다. 상신 이후 처리는 템플릿이 아니라 문서별 결재선을 기준으로 하여 과거 결재 흐름이 조직 변경의 영향을 받지 않도록 한다.

### 조직과 실시간 기능

* SSE 기반 결재 요청·처리 알림
* 결재함 실시간 카운트 갱신
* WebSocket 기반 결재건별 협업 채팅
* 작성자·결재자·참조자 채팅 참여 정책
* 결재 완료 시 채팅방 종료와 대화 내역 보존

### 통계와 운영

* 월·주 단위 결재 생성·완료·진행 통계
* `USER`의 소속 부서 집계 통계
* `ADMIN`의 담당 부서 상세 통계와 장기 미처리 현황
* `SUPER_ADMIN`의 조직 전체·부서 비교·사용자별 처리 현황
* 사용자별 통계 서버 인가와 감사 로그
* 관리자 작업 감사 로그
* 실제 조회 조건과 실행 계획을 근거로 한 인덱스 최적화

개인 순위나 성과 평가 화면은 만들지 않는다. Redis와 Kafka도 구체적인 병목이나 분산 처리 요구가 확인될 때만 검토한다.
